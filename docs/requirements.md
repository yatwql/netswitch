# 需求文档（Requirements）

> 项目：netswitch —— 多物理网卡切换与流量分流工具
> 状态：已评审，随设计迭代更新
> 说明：本文档已整合原始需求，是需求的唯一来源（网卡/路由等由运行时动态探测，不在此固化）。

## 1. 背景与目标

目标为一台 Debian Linux 主机，具备 **1~N 张物理网卡（数量不固定）** 以及供容器使用的虚拟网卡。网卡的名称、类型、IP、网关、metric、默认路由等**均在运行时自动探测**，不在本需求中固化。

主机上运行着容器（网桥 + veth + 网络命名空间），容器通过主机 NAT（MASQUERADE）出网。

> 常见情况：可能只有一张无线生效（有线未插网线），也可能同时生效多张无线；数量与状态以运行时探测为准。

需要一套程序，同时提供 **脚本（scripts/）** 与 **TUI 界面（src/）** 两种使用方式，功能完全一致，用于对物理网卡进行可配置化、可逆的运行时管理。

## 2. 术语

- **物理网卡（physical interface）**：机器的有线/无线实体网卡（运行时探测）。
- **metric（路由优先级）**：数值越小优先级越高；决定多默认路由下流量的实际出口。
- **默认路由**：`default via <网关> dev <网卡> metric <值>`。
- **策略路由（policy routing）**：通过 `ip rule` + 独立路由表，让特定流量走指定网卡。
- **fwmark**：内核数据包标记，配合 `ip rule fwmark` 选择路由表。
- **MASQUERADE / SNAT**：容器出网时把源地址改写为主机出口网卡 IP。
- **分流规则（rule）**：一条“把某类流量导向指定网卡”的通用策略，由规则名唯一标识（初始规则名为 `github`，可扩展更多）。

## 3. 功能需求（FR）

### FR1 — 临时关闭 / 开启物理网卡
- 可以**临时关闭**其中任意一张物理网卡（支持 1~N 张，数量不固定）。
- 可以**再次开启**这张物理网卡。
- 关闭后网卡不再承载流量；重新开启后由 DHCP/NetworkManager 自动恢复 IP 与路由。
- 保护：仅有一张物理网卡「生效」（唯一承载默认路由）时，**禁止关闭该网卡**（否则主机断网）。

### FR2 — 调整物理网卡的 metric 优先级
- 可以调整任意物理网卡的 metric。
- 支持「设置指定值」与「设为优先网卡」两种操作；优先/回退 metric 值可配置（默认 100/600）。
- 通过重建默认路由实现，不修改系统连接配置（运行时生效）。

### FR3 — 指定流量经指定网卡（初始为 GitHub，可扩展）
- 可以将某类流量（初始为 GitHub：git clone/push、API、网页、actions 等）指定走某张网卡（例如某张无线网卡）。
- **主机自身**发起的该类流量走指定网卡。
- **主机上的容器**对外访问该类流量时，同样走指定网卡。
- 其余流量不受影响，仍按默认路由/metric 走。
- 支持随时切换出口网卡、随时撤销（恢复走默认路由）。
- 分流规则通用化：未来可新增其他流量规则（如不同域名/网段走不同网卡），无需改动程序。

### FR4 — 全可配置化，不写死
- 网卡名、metric、网关、路由表 ID、fwmark、后端模式、CIDR 来源等全部来自配置文件；网卡类型自动探测（可覆盖）。
- 配置中未填写的字段自动探测（网关、当前 metric、IP 等）。
- **分流规则通用化**：规则名、CIDR 来源 URL/字段、出口网卡均为配置项；初始仅提供一条名为 `github` 的默认规则，可任意扩展。
- CIDR 列表可来自配置的 URL（初始为官方 `https://api.github.com/meta`），并支持手动补充、可离线缓存。

### FR5 — 脚本与 TUI 功能一致
- 提供命令行/脚本接口（`scripts/`）。
- 提供 TUI 界面（`src/`）。
- 两者共享同一套核心逻辑（`src/python/netswitch/`），保证行为完全一致。

### FR6 — 状态查询
- 展示：网卡名、类型（有线/无线，**高亮区分**）、IP、连接状态（已连接 / 未插网线 / 未有连接）、当前 metric、当前默认路由、各分流规则是否生效、生效网卡。
- TUI 进入时自动拉取实时网卡信息（数量/状态/类型），并支持手动刷新（`F`）。

### FR7 — 应用与撤销
- `apply`：按配置文件一次性应用全部设置（metric、全部分流规则），幂等；不主动改变网卡开关状态（开关是显式的一次性操作）。
- `revert`：撤销本程序做过的所有改动，恢复原始默认路由、清理策略路由规则。
- 支持 `--dry-run`：只打印将执行的命令，不真正执行。

### FR8 — 开机自恢复（systemd）
- 提供 systemd 服务，开机联网后自动应用配置（metric、全部分流规则）。

### FR9 — 网络自动探测与配置刷新
- 可自动探测当前机器的网络情形：物理网卡列表、有线/无线类型、连接状态（已连接/未插网线/未有连接）、IP、网关、metric、默认路由。
- 根据探测结果重新生成/刷新 `interfaces` 配置，替换机器相关旧值（不写死、可迁移到新机器）。
- 可从 CLI（`cli-netswitch.sh detect`）与 TUI（“重新探测网络”按钮）触发。
- 默认只读（打印拟生成配置）；`--write` 才写回，且仅更新 `interfaces`，保留 `rules` 等其它配置。

### FR10 — IPv6 分流（双栈）
- 分流规则的 CIDR 来源可包含 **IPv6 网段**（如 GitHub `/meta` 中的 v6 记录），手动 `cidrs.extra` 中的 v6 网段同样生效。
- 地址族可配：全局 `routing.ip_versions`（**默认 `["v4"]`，向后兼容**），可用 `rules[].cidrs.ip_versions` 按规则覆盖（例：只有某条规则走 v6，或某条规则只要 v4）。
- IPv6 出口网关取自 `interfaces[].gateway6`，缺省从当前 v6 默认路由自动探测（常见为 `fe80::1` 链路本地地址，带 `dev` 使用）。
- 三个后端均支持 v6：
  - nftables：`ipv6_addr` 集合 + `ip6 daddr` 打标 + `ip -6 rule fwmark`；
  - iprule：`ip -6 rule add to <v6-cidr>` + 独立表的 v6 默认/直连路由；
  - mainroute：`ip -6 route replace <v6-cidr> via <gw6> dev <网卡> proto 200`。
- **环境不具备 v6 时必须降级而非失败**：内核未启用 IPv6、出口网卡无 v6 网关、内核不支持 `CONFIG_IPV6_MULTIPLE_TABLES` 时，告警并跳过 v6，**v4 分流照常生效**。
- 清理同样只删本程序产物：v6 明细路由按 `proto 200` + 出口网卡 + 地址族判定，不得删内核 v6 直连路由与他人 v6 静态路由；v6 的 `ip rule`/路由表按同一签名清理。
- `status` 与 TUI 展示网卡 v6 地址/网关与每条规则参与的地址族。

### FR11 — 配置驱动的规则新增/删除（含域名与通配符）
- TUI 提供「新增规则」（`n`）与「删除规则」（`x`）菜单项；CLI 提供 `rule add` / `rule remove`。
- **新增规则时只写配置文件，不触碰网络**：新规则在下一次 `apply`（或按规则 `p` / 全局 `a`）时才作用到物理网卡。删除同理：只从配置移除，其已生效的分流产物在下次 `apply` 时被清理。
- 输入支持三种写法（可混合、逗号/空格/分号分隔）：
  1. 单个 IP（`1.2.3.4`、`2001:db8::1`）；
  2. CIDR 网段（`10.0.0.0/8`、`2001:db8::/32`）；
  3. 域名（`example.com`）与**通配符域名**（`*.github.com`）；直接粘贴 URL 时自动取主机名。
- 域名在 **apply 时解析**为 IP（A/AAAA）后参与分流，结果带 TTL 缓存；解析失败时回退缓存并告警。
- `*.example.com` 的语义：解析 apex，并做一次 **DNS 通配符探测**（随机标签查询）；
  **通配符 ≠ 所有子域**（DNS 无法枚举），需要精确覆盖时将具体子域一并列出；可用 `cidrs.wildcard_probe: false` 关闭探测。
- 新增规则默认名为 `custom-N`（自动避让重名），也允许通过 `--name` 指定。
- 写入前校验：规则名/网段/域名/出口网卡/地址族；写入后重新加载校验，失败则回滚文件内容。
- 与现有 `e`（选出口，立即重建）/ `c`（撤销规则分流，写配置+重建）的区别必须在文档与界面提示中明确：
  `n`/`x` 只改配置，`e`/`c`/`p`/`a` 会真正作用到网络。

## 4. 非功能需求（NFR）

- **容器覆盖（强制）**：所有分流规则必须同时作用于主机本机与主机上所有容器（网络命名空间）的对外流量，缺一不可。
- **权限**：所有操作需 root 权限；非 root 运行给出明确提示并拒绝。
- **可逆**：所有变更可被 `revert` 撤销；记录改动前的原始状态，且**重复 apply 不得污染 revert 基线**（原始状态只在首次 apply 时记录）。
- **幂等**：`apply` 重复执行安全、结果一致；`rule apply <name>` 也按配置全量重建，不影响其它规则。
- **安全**：
  - 干跑模式、变更前校验、危险操作二次确认。
  - **配置白名单校验**：标识符（`nft_table`/规则名）、数值（`table_id` 避开内核保留表、`fwmark` 非 0）、路径（`state_file`/`cache_file` 必须在数据目录内）非法时拒绝启动。
  - **只删自己的产物**：清理按签名识别（nft 表名 / 主表 `proto 200` 明细路由 / `pref ∈ [20000,32000)` 的 `ip rule`），不得删除内核直连路由或他人静态路由。
  - **先校验后改动 + 失败回滚**：预检不通过时不修改系统；重建失败时清理已建产物。
- **最小依赖**：零第三方 Python 运行时依赖（仅标准库）；核心依赖系统自带 `ip` 命令；nftables 后端在无 `nft` 时自动回退为纯 `ip rule` 模式。
- **日志**：记录执行的命令与结果到 `netswitch.log`（自动轮转）；仓库 `logs/` 不可写（如被 root 创建）时自动回退到用户可写目录并提示。

## 5. 约束

1. 目标系统：Debian Linux（含 systemd、iproute2）。
2. 目录结构固定：
   - `scripts/` 脚本（shell 便捷入口，调用 src/python 中的 CLI/TUI）
   - `src/python/` Python 源程序
   - `src/test/` 测试代码
   - `docs/` 文档（requirements.md / technical.md / plan.md / changelog.md / review-findings.md / test-plan.md / user-manuals.md / folder.md / faq.md）；根 `README.md`
   - `data/config/` 配置文件
3. 实现语言：Python 3（仅标准库）；TUI：curses；配置格式：JSON。
4. 地址族：支持 IPv4 / IPv6 双栈；`routing.ip_versions` 默认 `["v4"]`（与升级前行为一致），需要时可开启 v6。
5. 分流规则通用化：脚本/模块/配置键不得硬编码 `github`；初始默认规则名为 `github`。

## 6. 验收标准

- [ ] `apply` 后：所有网卡（1~N 张）metric 符合配置，默认路由正确。
- [ ] 关闭一张网卡后其默认路由消失，开启后恢复。
- [ ] 三张网卡/仅一张无线生效（有线未插网线）等场景可正常切换与分流。
- [ ] TUI 中未插网线/未关联的网卡明确显示「未插网线/未有连接」，有线/无线高亮可辨。
- [ ] 主机 `curl https://api.github.com`、`git clone` 出口 IP 为默认规则（github）指定网卡的公网 IP。
- [ ] 容器内访问 GitHub 的出口 IP 与指定网卡一致。
- [ ] 访问规则外站点（如 `curl https://example.com`）出口仍按默认 metric 走。
- [ ] 新增一条自定义规则后无需改程序即可分流其流量。
- [ ] `revert` 后 `ip route` / `ip rule` / nft 规则恢复原状；**重复 apply 多次后 revert 仍恢复到 DHCP 原始 metric**。
- [ ] 配置非法（`table_id: 254`、`backend: nftable`、`cache_file` 指向数据目录之外、规则名归一化重名）时在加载阶段报错，且不改动任何系统状态。
- [ ] 分流清理不会误删内核直连路由或他人 `proto static` 路由（netns 集成用例覆盖）。
- [ ] `install-systemd` 生成的单元能被 `systemctl start` 正常应用（参数顺序/配置路径正确）。
- [ ] 脚本与 TUI 对同一操作产生相同结果。
- [ ] 配置为空/缺字段时自动探测，程序不报错。
- [ ] 在新机器上运行 detect 能正确识别物理网卡并生成配置；`rules` 等其它配置不被覆盖。
- [ ] 未写 `routing.ip_versions` 时行为与升级前完全一致（仅 v4；v6 网段被忽略）。
- [ ] 配置 `routing.ip_versions: ["v4","v6"]` 且出口网卡有 v6 网关时，apply 后 v6 目标流量走指定网卡，v4 行为不变。
- [ ] 环境不具备 v6（未启用 IPv6 / 无 v6 网关 / 无 v6 策略路由）时，apply 仍成功且 v4 分流正常，告警说明 v6 已跳过。
- [ ] 清理不会删除内核 v6 直连路由或他人 v6 静态路由。
- [ ] TUI `n` 输入 `10.0.0.0/8 *.github.com` 后：仅 `config.json` 变化，`ip route`/`ip rule`/nft 无任何变化；`apply` 后新规则生效。
- [ ] 域名规则在 apply 时解析为 IP 并分流；`*.example.com` 能覆盖 apex 与（若存在）DNS 通配记录的地址；解析失败时回退缓存并告警。
- [ ] TUI `x` 删除规则后：配置里不再有该规则，当前已生效状态不变，`apply` 后其分流产物被清理。
- [ ] 非 root 运行被拒绝且提示明确。
